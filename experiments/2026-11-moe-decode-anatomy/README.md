# MoE の decode 1 トークンはどこに時間を使っているか(2026-11-moe-decode-anatomy)

Qwen3.6-35B-A3B(IQ3_S、全部 VRAM)の decode は 160 tok/s 前後で、4080 SUPER の帯域を半分も使っていないように見える。1 トークンの時間を「固定費 + 帯域で決まる読み出し + 文脈長」に分解し、どの項が支配的かを測る。あわせて llama.cpp を build 12182 から 12464(1.0 系)に上げたときの差を見る。

## 結論

**MoE の decode は半分が帯域、半分が「カーネル 1 本あたりの固定費」で、experts の読み出しは 2 割しかない。** k=8(既定)の 6.25 ms の内訳は次のとおり(build 12464、CUDA graph あり)。

| 項                                             | 時間        | 割合 | 根拠                                                     |
| ---------------------------------------------- | ----------- | ---- | -------------------------------------------------------- |
| 固定費(3,939 ノード × 0.68 µs)                 | **2.68 ms** | 43%  | t(k) の切片から密部分の帯域時間を引いた残り              |
| 毎トークン全部読む部分(1.67 GB、696 GB/s)      | 2.41 ms     | 38%  | GGUF のテンソル表と、密モデル 2 量子化から出した実効帯域 |
| experts の読み出し(8 本 × 45 MB、**312 GB/s**) | 1.16 ms     | 18%  | t(k) の傾き 0.145 ms/k(R²=0.998)                         |

- 固定費を消せれば 280 tok/s、experts を密な読み出しと同じ効率で読めれば 0.6 ms 縮む。量子化を詰めても experts の 18% にしか効かない
- llama.cpp 1.0 系への更新(b12182 → b12464)は decode を 0.6% 速くしただけ。ノード数は 3,939 で変わらず、固定費も残った。`GGML_CUDA_GRAPH_OPT=1` も効かない
- 文脈長の項は 1k トークンあたり 0.042 ms(0 → 64k で 5.95 → 8.71 ms)。64k を超えると固定費より大きくなる

## なぜそうなるか

- **毎トークン全部読む部分が 1.67 GB もある。** output(0.42 GB)、attn_qkv(0.41)、attn_gate と ssm_out(各 0.21)、shared expert(0.10)などが Q6_K で、3B 活性という数字から想像するより重い。experts は IQ2_S / IQ3_S と細かく量子化されているので 1 本 45 MB(全 40 層の合計)しかない
- **experts の実効帯域が密の半分。** 1 層 1 expert あたり gate / up / down で約 1.1 MB の小さな塊を、ルーティングで選ばれた位置から 8 個ずつ読む。連続した大きな行列を読む密の matmul(696 GB/s、ピークの 95%)ほど帯域を使い切れない
- **固定費はカーネル数に比例する。** MoE のグラフは 3,939 ノード(GDN、ルータ、norm などの小さな演算が多い)、9B 密は 2,001 ノード。1 本あたり 0.68〜0.97 µs で、CUDA graph を切ると +0.9 ms(1 本 0.91 µs)に増える。グラフ最適化で変わらないので、起動の手間ではなく、小さなカーネルそれぞれの実行時間の下限と見るのが妥当
- **過去の実験がこの式で説明できる。** 電力を絞っても decode が 6% しか落ちなかった(power-limit)のは、固定費と帯域の項がどちらも SM クロックにほとんど依存しないから。IQ3_S と IQ3_XXS で速度差が無かったのは、違いが experts(全体の 18%)にしか無いから。MTP の検証(n+1 トークンを 1 回で流す)がほぼ無料だったのは、固定費が 1 回の forward ごとにかかり、トークン数で割られるから

## 計測条件

- モデル: unsloth `Qwen3.6-35B-A3B-UD-IQ3_S`(arch `qwen35moe`、256 experts、既定 k=8、40 層)。対照に `Qwen3.5-9B` の Q8_0 / Q4_K_M(密、同じグラフで重みのバイト数だけ違う)
- サーバ: `-ngl 99 --flash-attn on -np 1 -c 8192 -ctk q8_0 -ctv q8_0 -b 2048 -ub 512 --no-mmproj`(本番の llama-swap 構成に合わせた)。k は `--override-kv qwen35moe.expert_used_count=int:k` で 1〜16 に変えた
- CUDA graph: 既定(on)、`GGML_CUDA_DISABLE_GRAPHS=1`(off)、`GGML_CUDA_GRAPH_OPT=1`(opt、k=1/8/16 のみ)
- ノード数: `-lv 4` のときに出る `sched_reserve: graph: nodes = N` を採取
- 1 トークンの読み出しバイト B(k): GGUF のテンソル表から `scripts/gguf_bytes.py` で算出。expert テンソルは n_bytes / 256 を 1 本分、token_embd は 1 行分、それ以外は毎トークン全部
- 文脈長: `llama bench -p 0 -n 128 -d 0,4096,16384,32768,65536 -r 3`(k=8)
- llama-swap 本体は計測中アイドル(VRAM 80 MiB)を毎回確認してから起動した

## 結果

### k 掃引(ms / トークン、b12182 → b12464)

| k   | graph あり                 | graph なし  |
| --- | -------------------------- | ----------- |
| 1   | 5.30 → 5.28                | 6.22 → 6.21 |
| 2   | 5.38 → 5.35                | 6.28 → 6.26 |
| 4   | 5.73 → 5.67                | 6.59 → 6.58 |
| 8   | 6.29 → **6.25**(160 tok/s) | 7.17 → 7.17 |
| 12  | 6.83 → 6.79                | 7.70 → 7.69 |
| 16  | 7.49 → 7.46                | 8.42 → 8.43 |

当てはめ(b12464、graph あり): t(k) = 5.09 + 0.145·k ms(R²=0.998)。密モデル対照から BW_dense = 696 GB/s、密の固定費 1.95 ms(2,001 ノード)。詳細は `results/fit-*.json`、全点は `results/k-sweep.csv`。

### 密モデル対照(Qwen3.5-9B、b12464)

| 量子化 | 毎トークンの読み出し | graph あり | graph なし |
| ------ | -------------------- | ---------- | ---------- |
| Q8_0   | 8.44 GB              | 14.06 ms   | 14.64 ms   |
| Q4_K_M | 5.10 GB              | 9.27 ms    | 9.81 ms    |

### 文脈長(k=8、llama bench)

| 深さ | b12182  | b12464  |
| ---- | ------- | ------- |
| 0    | 6.00 ms | 5.95 ms |
| 16k  | 6.55 ms | 6.52 ms |
| 32k  | 7.22 ms | 7.22 ms |

サーバ経由(6.25 ms)と llama bench(5.95 ms)の差 0.3 ms は、サーバ側の 1 トークンごとの処理(サンプリング、スロット管理)。

## 落とし穴

| 罠                                         | 症状                                                          | 対処                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| llama-swap のイメージに llama-bench が無い | `/app` には `llama`(統合バイナリ)と `llama-server` だけ       | `llama bench` サブコマンドを使う。ただし `--override-kv` は無いので k の掃引はサーバで |
| グラフのノード数が既定のログに出ない       | `graph nodes` を grep しても空                                | `-lv 4` で起動すると `sched_reserve: graph: nodes = N` が出る                          |
| 旧ビルドとの比較                           | イメージを pull すると `:cuda` が上書きされ、旧ビルドが消える | pull 前に `docker tag ... llama-swap:b12182` で退避                                    |

## 次

- 固定費 2.7 ms の中身を Nsight Systems で見る(短いカーネルの実行時間か、カーネル間の空きか)。GPU 機に nsys が無いので導入から
- 固定費は forward 1 回ごとにかかるので、投機デコードや並列スロットで「1 回に流すトークン数」を増やすほど薄まる。この式を前提に、案 2(投機で出力が分岐する理由)と案 6(prefill の有効行数)へ進む
