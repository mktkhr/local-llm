# 投機デコード: Qwen3.6-35B-A3B の MTP / ngram を 16 GB で測る(2026-10-speculative-decoding)

RTX 4080 SUPER (16 GB) 上の Qwen3.6-35B-A3B に対して、MTP ヘッド / n-gram / 外部 draft による投機デコードが decode を速くするか、Claude Code の実ワークロードで受理率はいくつか、`--n-cpu-moe` と prefix cache の下でも利得が残るかを測る。

## 結論

1. **Claude Code のバックエンドには入れない。** 実タスク(M1 / M2 × 2 回)の合計所要時間は MTP n=1 で +7%、n=2 で +21%(現行構成比)。勝ち条件「15% 以上短縮」を満たさない。tool_use の構造は 903 回中破損 0、prefix cache も維持(ヒット率 0.90〜0.95)で**品質面の問題は無い**が、実セッションは思考の軌跡(ターン数・1 ターンの出力長)のばらつきが decode の利得を飲み込む
2. **decode 自体は実セッションでも確かに速い。** 有効 decode は none 120 tok/s → n=1 で 152(+26%)、n=2 で 175(+46%)。ただし wall time のうち decode は 41〜60% で、残りは prefill とクライアント側。MTP が wall に効く上限は理論上 15〜20% しかなく、n=2 の試行では軌跡の差(1 ターンの出力 135 → 267 トークン)に埋もれた
3. **チャット・要約・思考の用途には強い。** 合成ワークロードで MTP n=2 は要約 +45%、思考 +57%、コード書き換え +31%(3 ブロック、ばらつき ±0.02)。しかも平均電力が 20〜30 W 低い。open-webui からの対話用に `qwen36-35b-iq3xxs-mtp2` を**別エントリとして足す価値はある**(Phase 4 の判断は利用者に委ねる)
4. **MTP は全層 GPU が前提。** `--n-cpu-moe 13` のオフロード構成では受理率が同じ(0.8〜0.97)でも利得が +0〜13% に落ちる。検証バッチが CPU 側 expert を通るコストが受理の稼ぎを食う
5. **MTP の代償は VRAM 約 2.4 GB**(重み +1.6 GB、起動後の draft context +0.85 GB)。16 GB では IQ3_S → IQ3_XXS の格下げと n-max=3 の断念を強いた。ただし IQ3_XXS の decode は IQ3_S と 1 tok/s も違わなかった(220 W 制限下)
6. **n-gram はコード書き換えの一部だけ 2 倍、他は無害か逆効果。** 既存コードの長いブロックを書き出す W2-03 で 2.13 倍(3 回再現)、新規コードでは 0.69 倍。MTP との併用は MTP を邪魔する。単独で「エディタ用途」に限るなら選択肢
7. **投機デコードは出力保存的でない**(同じプロンプト・greedy でも生成物一致率 0〜0.67)。tool_use の形式は無傷だったが、内容面の等価性は保証されない

## なぜそうなるか

- **利得 = 受理率 × (検証 1 回で得るトークン数) − draft のコスト。** フル GPU では draft(MTP ヘッド 1 層)が軽く、受理率 0.75〜0.95 なら n=2 で 1.3〜1.6 倍になる。CPU オフロードでは検証バッチ(n+1 トークン)が CPU 側 expert を通り、1 ステップのコストが n に比例して増えるため、受理で稼いだ分を失う
- **Claude Code の 1 ターンは短い。** 出力 120〜270 トークン、prefill は 90% 以上がキャッシュヒット。1 ターン 2〜4 秒のうち decode は 1〜2 秒で、残りはキャッシュ外の prefill(1〜2 秒)と Claude Code 側の処理。decode を 1.5 倍にしても 1 ターン 0.3〜0.7 秒しか縮まず、ターン数が 1 つ増えれば消える
- **n-gram は「過去に出た並び」しか draft できない。** 既存コードをそのまま書き出す場面では長い draft が当たり続けて 2 倍になるが、新規生成では外れ続けて検証コストだけ払う

読みどころ:

- **IQ3_XXS への格下げは decode を 1 tok/s も落とさなかった。** 現行 C(IQ3_S)と C' none の decode は 4 ワークロードとも一致(96 / 91 / 150 / 150)。220 W 制限下では重みの読み出し量の差が速度に出ない。よって C' の比はそのまま現行構成に対する比として読める
- **フル GPU では MTP が全ワークロードで勝つ。** n-max=2 で要約 +45%、思考 +57%、コード書き換え +31%、長文 tool_use +14%。利得は受理率に比例し、tool_use の JSON(受理 0.74)より自然文・思考(0.89)で大きい。n-max=1 は受理率が高い(0.86〜0.96)ぶん安定で、W1 では n=2 より速い
- **CPU オフロード(B')では利得がほぼ消える。** 受理率は C' と同等(0.8〜0.97)なのに +4〜13%、W1 では ±0。検証バッチ(n+1 トークン)が CPU 側 expert を通るぶん 1 ステップのコストが増え、受理で稼いだ分を食う。**MTP は「全層 GPU に載っていること」が前提**(問い 1 の答え)
- **n-gram はコード書き換えだけ強烈に効き、それ以外は無害か逆効果。** W2-03(Write で既存コードの長いブロックを書き出す)で ngram-simple **2.13 倍**、ngram-mod 1.91 倍、3 ブロックとも再現。W2-01(新規コード)では 0.69 倍。draft が出ない W3 / W4 は 1.00。MTP と併用すると n-gram の低品質 draft が MTP を邪魔して W1 で 1.14 → 1.05 に落ちる。**単独なら「エディタ用途は ngram、それ以外は MTP」、併用はしない**
- **MTP の VRAM コスト**: 重み +1,592 MiB(IQ3_S)に加え、起動後の draft context で **+830〜890 MiB**(none 15,024 → mtp 15,854〜15,918 MiB)。合計約 2.4 GB。16 GB では IQ3_S → IQ3_XXS の格下げと mtp3 の断念を強いた。decode は落ちなかったので、品質差(Phase 2 の tool_use 破損)だけが代償
- **出力は保存されない。** mtp の生成物一致率 0〜0.67(同じプロンプト・greedy でも baseline と別のトークン列)。n-gram で draft が出なかった行だけ 1.0。tool_use が壊れるかは Phase 2 で見る
- **電力**: C' で mtp2 は none より平均電力が低い(W3: 168〜187 W vs 195〜207 W)のに 1.45 倍速い。tok/s/W では 1.6〜1.7 倍。220 W 制限下で C' の prefill は上限に張り付く(max 223〜226 W)。B' は CPU 律速で 106〜115 W
- **W1/W2 の prefill は cold。** 3 本のプロンプトは別セッション由来で共通 prefix が無く、`-np 1` では直前のプロンプトの KV しか残らないため、W1 を warm で測る設計は成立しなかった。warm prefix の挙動は Phase 2 の実セッションで `cache_n` を見る

- 受理率は実セッションでも高い(mtp1 0.95、mtp2 0.89〜0.92)。合成 W1(0.74〜0.86)より上で、実際の出力には自然文の説明が混ざるため
