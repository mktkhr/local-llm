# greedy なのに投機デコードで出力が変わるのはなぜか(2026-11-greedy-divergence)

投機デコードは「target が自分で選ぶトークンと一致したものだけ受理する」ので、greedy なら投機なしと同じ出力になるはずだが、実際には途中から別の文章になることがある。投機の検証(n+1 トークンを 1 回の forward で流す)は decode と別のカーネル経路を通り、ロジットがわずかに揺れる。この揺れ δ が、1 位と 2 位の差(余裕 m)を超えて逆転させたときに分岐する、というハザードモデルを立て、分岐の回数と位置を予測できるかを確かめる。

## 結論

**分岐の原因は投機の検証バッチだけで、起きるのは余裕 0.15 nats 未満の接戦の位置に限られる。回数は「余裕の小さい位置での揺れの分布」から予測でき、予測 8.5 件に対して観測 7 件だった。**

- **投機なしは完全に決定的。** 投機なしを 2 回流すと、4 構成 × 17 プロンプトのすべてでトークン列も logprob もビット単位で一致した。投機ありでも draft が一度も出なかった実行は投機なしと完全に一致する。逆に、draft が全部棄却された実行(14 draft、受理 0)でも揺れは始まる。分岐を決めるのは「受理したか」ではなく「検証をバッチで流したか」
- **揺れの大きさは MoE で 3.7 倍。** |δ| の中央値は Qwen3.6-35B-A3B(IQ3_S)で 0.16 nats、Qwen3.5-9B(密)で 0.044 nats。密モデルは Q8_0 と Q4_K_M で中央値が同じ 0.044 だったので、量子化のビット数ではなく MoE 側の構造が揺れを増幅している(ルータの top-k 選択が接戦で入れ替わる、が有力。直接の確認は案 4 に回す)
- **分岐は 102 実行中 7 回、すべて余裕 0.0017〜0.15 nats の位置。** 400 トークンの生成 1 回あたりの分岐率は、観測で MoE 4/68(6%)、密 3/34(9%)、予測(余裕 < 4 の分布)で 9% / 8%(ngram 投機、受理率 79〜90%)
- **素朴なハザードモデルは過大に予測する。** 全位置の δ の分布で h = P(δ < −m) を積むと予測 10.5 件(ポアソンで観測 7 件以下になる確率 0.18)。余裕 4 nats 未満の位置の δ だけで分布を作ると予測 8.5 件(同 0.39)で、build × 方式ごとの値もおおむね合う。MoE では接戦の位置の揺れが全体より小さい(中央値 0.05〜0.13 vs 0.165)
- **llama.cpp 1.0 系への更新は揺れを変えなかった。** |δ| 中央値は b12182 で 0.165、b12464 で 0.162。few-row MMQ などの変更は分岐の起きやすさに影響しない
- 量子化の比較や回帰テストのように greedy の再現性に頼る評価では、投機デコードを切っておく必要がある。速度は 2.7 倍になるが、400 トークンあたり 6〜9% の確率で途中から別の出力になる

## なぜそうなるか

- **検証は decode と別の計算経路を通る。** decode は 1 行、検証は数行を一度に流すので、行列積・attention・GDN で選ばれるカーネルや分割のしかたが変わる。数学的には同じ値でも、浮動小数の足し順が変わるので結果がわずかにずれる
- **一度ずれると以後ずっと揺れる。** 検証で計算した K/V と GDN の状態がキャッシュに残るので、揺れ始め以降は δ = 0 の位置が 1 つも無かった(全構成で 0%)。分岐の機会は「揺れ始め以降の全位置」になる
- **逆転は余裕より大きな負の揺れが来たときだけ起きる。** 1 位と 2 位の logprob 差 m が 8 nats 以上の位置が MoE で 96%、密で 92% を占め、0.3 nats 未満の位置は 1 実行あたり平均 0.3〜1.1 個しかない。揺れの中央値は 0.04〜0.16 nats なので、分岐は「数少ない接戦の位置に、たまたま大きめの揺れが当たったとき」に限られる
- **MoE で揺れが大きいのは、離散的な選択があるからと考えるのが自然。** 密モデルは量子化を Q8_0 から Q4_K_M に変えても揺れが変わらない(0.044 / 0.044)。浮動小数の誤差そのものは小さく、それを不連続に増幅する仕組み(接戦の expert の入れ替わり)が MoE にだけある
- **接戦の位置で揺れが小さい理由はまだ説明できていない。** 「接戦の 2 トークンは出力埋め込みが近いので、同じ隠れ状態の揺れでも差が小さく出る」と考え、lm head の行の差のノルム ||w_a − w_b|| で δ を割ってみたが、MoE では接戦の位置のノルムがむしろ大きく(中央値 1.03〜1.12 vs 全体 0.91)、予測も悪化した(Q4_K_M を除く 5 組で 9.6 → 10.8 件)。この仮説は棄却

## 計測条件

- モデル: unsloth `Qwen3.6-35B-A3B-UD-IQ3_S`(MoE、build 12182 と 12464)、`Qwen3.5-9B` の Q8_0 / Q4_K_M(密、build 12464 のみ)
- サーバ: `-ngl 99 --flash-attn on -np 1 -c 16384 -ctk q8_0 -ctv q8_0 -b 2048 -ub 512 --no-mmproj --metrics`。投機は `--spec-type ngram-simple` / `ngram-mod`(draft モデル不要の 2 種)。投機なしは 2 回(none / none2)
- 生成: `/apply-template`(thinking off)で整形し、`/completion` に `temperature: -1`(greedy で確率は生の softmax)、`n_probs: 5`、`n_predict: 400`、`cache_prompt: false`
- プロンプト: このリポジトリのコード片を「小さな変更を加えて全体を書き直す」14 本(n-gram の draft が当たる型、`scripts/make_prompts.py` が行範囲で切り出す)と、10 月実験の推論プロンプト W4 の 3 本
- 余裕 m_i: 投機なしの位置 i での 1 位と 2 位の logprob 差。揺れ δ_i: 投機ありでの同じ 2 トークンの logprob 差から m_i を引いたもの(分岐位置まで。文脈が同じなので比べられる)
- 予測: 揺れ始め(最初に δ ≠ 0 になる位置)から分岐位置(分岐しなければ末尾)まで h_i = F(−m_i) を積み、P(分岐) = 1 − Π(1 − h_i)。F は δ の経験分布。評価は実行ごとの Brier スコアと、合計件数のポアソン検定
- 速度の列は `n_probs` 付きの値(全語彙の softmax が入るので、MoE の投機なしは 160 tok/s ではなく 115 tok/s になる)。投機の倍率の目安にだけ使う

## 落とし穴

| 罠                                   | 症状                                                              | 対処                                                                          |
| ------------------------------------ | ----------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 短いプロンプトでは draft が出ない    | n-gram の投機は写しの無い文章でほぼ発火せず、揺れも分岐も起きない | 既存コードを少し変えて書き直させるプロンプトにした(1 実行あたり draft 約 300) |
| `n_probs` で decode が遅くなる       | MoE の投機なしが 160 tok/s ではなく 115 tok/s                     | 速度は投機の倍率の目安にだけ使う。絶対値は 2026-11-moe-decode-anatomy を参照  |
| draft 0 の実行を母数に入れると薄まる | 投機ありでも検証が一度も無ければ投機なしと完全一致する            | 揺れ始め(最初に δ ≠ 0 の位置)から数える                                       |

## 次

- 案 4(expert の参照トレース)で、揺れの大きい位置で expert の選択が入れ替わっているかを直接見る。入れ替わりの有無で δ を層別できれば、MoE の増幅を定量化できる
- 接戦の位置で揺れが小さい理由(MoE だけに見える)は未解決。接戦の位置を数百点集めるには、余裕の小さい位置を多く含むプロンプト(自由文の要約など)で回数を増やす必要がある
