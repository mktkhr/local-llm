# MoE の prefill は ubatch あたり expert の重みを何回読むかで決まる(2026-11-moe-prefill-tiles)

MoE の prefill では、ubatch のトークンが 256 個の expert に振り分けられるので、1 expert が受け取る行は平均 ub·k/E(k=8、E=256 なら ub/32)しかない。本番の `-ub 512` なら 16 行。行が少ないと行列積の効率が落ちるはずなので、実際の Claude Code のプロンプトのルーティングから ubatch ごとの expert 別の行数を数え、prefill 速度を説明する式を立てる。あわせて llama.cpp build 12182 と 12464(1.0 系)を比べる。

当初は「1.0 系の few-row MMQ(2〜24 行向けの新カーネル)が `-ub 512` の expert に効く」と予想していたが、ソースを読むと few-row MMQ は密な行列積(`ggml_cuda_mul_mat`)専用で、MoE の expert(`MUL_MAT_ID`)には使われない。そこで問いを「行数の少なさは何を通じて速度に効くのか」に組み替えた。

**完了(2026-11-21)。**

## 結論

**prefill の 1 トークン時間は「計算の下限 126 µs」+「ubatch ごとに 1 回読む重み(密部分と、その ubatch で使う expert)/ 364 GB/s」で説明できる(R² = 0.994)。`-ub 512` では重みの読み出しが 1 トークン時間の 3 分の 1 を占め、`-ub 2048` にすると prefill が 28% 速くなる。**

| ubatch | prefill(トークン / 秒) | 1 トークンあたり読む重み | うち expert | VRAM(`-c 36864`) |
| ------ | ---------------------- | ------------------------ | ----------- | ---------------- |
| 64     | 2,319                  | 113 MB                   | 86.9 MB     | 13,552 MiB       |
| 128    | 3,125                  | 69 MB                    | 55.9 MB     | 13,564 MiB       |
| 256    | 3,992                  | 40 MB                    | 33.6 MB     | 13,586 MiB       |
| 512    | **5,551**              | 22 MB                    | 19.1 MB     | 13,630 MiB       |
| 1,024  | 6,692                  | 12 MB                    | 10.3 MB     | 13,750 MiB       |
| 2,048  | **7,110**              | 6.2 MB                   | 5.4 MB      | 14,030 MiB       |
| 4,096  | 7,171                  | 3.1 MB                   | 2.7 MB      | 14,590 MiB       |

build 12464 の値。12182 は全点で 0.3〜0.7% 遅いだけ。

- **効いているのはタイルの埋まり方ではなく、重みを読む回数。** MMQ のタイルの埋まり率(実際の行 / 詰め物込みの行)は、`-ub 512` 以上で 0.63〜0.67 とほぼ一定だった。埋まり率が同じでも、ubatch が大きいほど同じ expert の重み 1 回の読み出しを多くのトークンで分け合える。1 トークンあたりに読む expert の重みは 512 で 19.1 MB、2048 で 5.4 MB
- **ubatch 内では、同じ expert の重みを読み直していない。** 「タイルごとに expert の重みを読み直す」モデル(R² 0.978)より、「ubatch 内で使う expert を 1 回ずつ読む」モデル(R² 0.994)のほうが合う。1 expert が 2 タイル以上に分かれても、2 枚目は L2 キャッシュから読めていると考えられる
- **実効 364 GB/s は decode の experts(312 GB/s)と同じ水準。** 1 層 1 expert あたり約 1.1 MB の塊を、選ばれた位置から飛び飛びに読む形なので、密な読み出し(696 GB/s)の半分ほどにとどまる(2026-11-moe-decode-anatomy と同じ理由)
- **本番の `-ub 512` を 2048 にすると prefill は 5,551 → 7,110 トークン / 秒。** VRAM は 400 MiB 増える。4096 まで上げても +0.9% しか伸びず、VRAM はさらに 560 MiB 増える
- **llama.cpp 1.0 系の更新は prefill を変えなかった。** few-row MMQ は MoE の expert には使われず、`MUL_MAT_ID` の空タイル省略(#32067)の効果も 1% 未満

## なぜそうなるか

- **MMQ は expert ごとに、届いた行を J 列ずつのタイルに分けて計算する。** J は「expert あたりの平均行数 ceil(ub·k/E)」を覆う最小の 8 の倍数(上限 128)で、ubatch ごとに決まる(`ggml_cuda_mmq_get_J_best`)。expert e に n_e 行届くと ceil(n_e / J) 枚のタイルになる
- **ルーティングには偏りがあるので、平均どおりには届かない。** `-ub 512` では 1 層あたり 256 expert 中 222 個に行が届き、J = 16 に対して 1 expert あたり平均 1.7 枚のタイルになる。平均より多く届いた expert はタイルが 2 枚になり、少ない expert はタイルの大半が空になる。この打ち消し合いで、埋まり率は ubatch によらず 0.63〜0.67 に落ち着く
- **1 回の ubatch で読む重みはほぼ一定で、トークン数で割られる。** 密部分(attention、GDN、shared expert、output など 1.67 GB)は ubatch ごとに 1 回、expert は届いた分だけ 1 回ずつ読む。`-ub 512` 以上では 1 層あたりの活性 expert が 222〜254 個とほとんど変わらないので、1 トークンあたりの読み出しはほぼ 1/ub で減る
- **残りの 126 µs は ubatch の大きさでは減らない部分。** 行列積の演算そのもの、3.2 万トークンの文脈に対する attention、GDN の再帰計算などで、トークン数に比例する

## 計測条件

- モデル: unsloth `Qwen3.6-35B-A3B-UD-IQ3_S`(全部 VRAM)
- サーバ: `--jinja -ngl 99 --flash-attn on -np 1 -c 36864 -ctk q8_0 -ctv q8_0 -b max(2048, ub) -ub ub --no-mmproj`
- プロンプト: 10 月実験で ccshim のログから抜いた Claude Code の実リクエスト W1-03(33 ツール、103 メッセージ)をサーバのテンプレートで整形し、先頭 32,768 トークンに切ったもの(リポジトリには入れない)。`/completion` にトークン列で渡し、`cache_prompt: false`、3 回の中央値
- ルーティング: build 12464 を `-cmoe --moe-cache-mib 11100 -b 32 -ub 32` で起動し、`LLAMA_MOE_CACHE_TRACE` で同じ 32,768 トークンの prefill を記録した(MoE cache のトレースは 32 トークン以下のバッチだけを記録するため)。ubatch ごとの行数は、記録したトークン列を ub トークンずつに区切って数えた
- 最終層(層 39)は prefill では出力トークンの分しか計算されない(llama.cpp の最適化)ので、トレースにも 3 トークンしか無い。集計から外した
- 当てはめた式(1 トークンあたり、µs)
  - M0: t = a + c / ub(ubatch ごとの固定費だけ)
  - M1: t = a + (1,674 MB / ub + タイルごとに読み直す expert の重み) / BW
  - M2: t = a + (1,674 MB / ub + ubatch 内で使う expert を 1 回ずつ) / BW

## 落とし穴

| 罠                                            | 症状                                                                 | 対処                                                                                        |
| --------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| few-row MMQ は MoE の expert に使われない     | 「1.0 系で `-ub 512` の prefill が速くなる」という予想が成り立たない | `ggml_cuda_should_use_mmq_few` の呼び出し元が密な行列積だけであることを確認して問いを変えた |
| prefill のルーティングは既定では記録されない  | MoE cache のトレースは 32 トークン以下のバッチだけ                   | `-ub 32` で流して全トークン分を取り、あとで任意の ubatch に区切り直す                       |
| 最終層のトレースが極端に短い                  | 層 39 だけ 3 トークン                                                | prefill では最終層が出力行しか計算しないため。集計から外す                                  |
| `llama bench` の prefill はランダムなトークン | ルーティングが実際の文章と違う                                       | サーバに実プロンプトのトークン列を渡して測った                                              |

## 次

- 本番の構成(128k 文脈、`-ub 512`)で `-ub 2048` が VRAM に収まるかを確かめる。C 構成(IQ3_S、全部 VRAM)は ub 512 で 15.0 GB 使っているので、+400 MiB は際どい
- `--n-cpu-moe` で experts の一部を RAM に置く B 構成では、大きな ubatch は「RAM から送る expert の回数」も減らすので、効果はもっと大きいはず。B 構成で同じ掃引をする
- 密部分 1.67 GB を毎 ubatch 読む費用は、ubatch を大きくする以外に減らせない。prefill と decode を同じ forward に詰める(チャンク prefill と decode の同居)と、decode 側の固定費とあわせて薄められる
