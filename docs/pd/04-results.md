# PD分離 PoC — Phase 2/3: クロスバックエンド検証と計測結果

CUDA (RTX 4080 SUPER) で保存した KV キャッシュを Metal (Apple M1) で restore し、再 Prefill なしに Decode を継続できることを確認した記録です。

- 実施日: 2026-08-29
- 結果: **PASS。両方向 (CUDA→Metal / Metal→CUDA) で成立**

## 1. 結論

**[01-research.md](01-research.md) のソース読解どおり、slot 保存ファイルはバックエンド非依存でした。**

全 30 試行 (構成 C 3 方式・D × 5 種のプロンプト長) で `residual_prefill_tokens = 1` であり、再 Prefill は発生していません。生成テキストも単体構成と同一で、KV が意味的に正しく復元されていることを確認しました。

**Wi-Fi 経由の実測で、1k トークンから 16k トークンまで全長で PD分離が M1 単体を上回りました。** 16,012 トークンでは M1 単体の 139.8 秒に対し 15.6 秒で、8.94 倍の短縮です。

ただしこの結果は転送方式に強く依存します。初回測定 (Python `http.server` / 単一接続) では 1k で PD分離が負けていました。nginx へ変更し Range で 8 並列取得するようにして初めて上記の値になります (§3、§5)。

10GbE 相当では最大 33.1 倍が見込めますが、**Wi-Fi の並列転送だけで 1GbE 相当 (10.12x) にほぼ到達している**点に注意が必要です (§8.2)。

## 3. ネットワーク実測と、単一 TCP フローの落とし穴

4080 は有線 (1000 Mbps リンク)、M1 は Wi-Fi 802.11ax / 5GHz / 80MHz です。

### 3.1 最初の測定では下りが極端に遅く見えました

| 方向 | スループット | 備考 |
| --- | --- | --- |
| M1 → 4080 | 737 Mbps | |
| **4080 → M1** | **255 Mbps** | 再送 294 回 |

PD分離で使うのは遅く見えた側 (4080 → M1) です。

### 3.2 原因は「Wi-Fi の容量」ではなく「単一 TCP フロー」でした

原因を切り分けた結果です。

| 検査項目 | 結果 | 判定 |
| --- | --- | --- |
| M1 の信号品質 | -37 dBm / Noise -91 dBm (SNR 54 dB) / MCS 11 | RF 起因ではない |
| 4080 の NIC | `enp39s0` speed=1000 / エラー 0 | 有線側は正常 |
| iperf3 単一フロー (下り) | 339 Mbps | |
| **iperf3 並列 4 フロー (下り)** | **764 Mbps** | **リンク容量は上りと同等** |
| RTT (ゲートウェイ) | min 4.4 ms / avg 6.3 ms | LAN としては大きい |

**下りのリンク容量は 764 Mbps あり、上り (737 Mbps) と同等でした。頭打ちは 1 フローあたりで発生していました。**

RTT 6.3 ms で 764 Mbps を 1 フローで維持するには約 588 KB のウィンドウが必要です。実測 339 Mbps は約 261 KB 相当でした。macOS の `net.inet.tcp.autorcvbufmax` は 4 MB あり上限には達していないため、**再送によって輻輳ウィンドウが繰り返し半減し、単一フローでは回復しきらない**のが実態です。並列フローは各々が独立に回復するためパイプが埋まります。

上りが速く見えたのは送信側が M1 だからです。Wi-Fi クライアントは自分の送信タイミングを制御できますが、受信は AP のバッファリングと再送に晒されます。この非対称は Wi-Fi の構造に由来します。

### 3.3 転送方式による差 (613 MiB の実測)

| 方式 | 実効 |
| --- | --- |
| Python `http.server` / 単一接続 | 15〜34 MiB/s |
| nginx / 単一接続 | 60.2 MiB/s |
| **nginx / 8 並列 Range** | **90.8 MiB/s** |

並列取得したファイルは sha256 が一致しており、データ破損がないことを確認済みです。

この結果を受けて構成を 2 点変更しました。

- [deploy/pd/compose.yml](../../deploy/pd/compose.yml) の `kv-http` を Python `http.server` から **nginx** へ変更 (Python の `http.server` は Range 非対応のため)
- [scripts/pd/pd_run.py](../../scripts/pd/pd_run.py) に `--conns` (既定 8) を追加し、Range で分割して並列取得するようにしました。配信側が Range 非対応なら単一接続へ自動的に退避します

生成テキストは M1 単体で同じプロンプトを処理したときと同一でした。KV が単に「読み込めた」のではなく、意味的に正しく復元されていることの証拠です。

## 8. 考察

### 8.1 当初の想定は外れました

[01-research.md](01-research.md) では「初回は転送が律速で PD分離が遅くても問題ない」と想定していましたが、**実測では全長で PD分離が勝ちました。**

理由は M1 の Prefill が想定以上に遅かったことです。当初 300 tok/s と仮定していましたが、実測は 1k で 206 tok/s、16k では 114 tok/s まで落ちました。アテンションが二次で効くため、長文ほど M1 が不利になります。

一方 KV サイズはトークン数に対して線形にしか増えません。**「二次で増える Prefill 時間」対「線形に増える転送時間」という構図であり、長文になるほど PD分離が有利になります。**

### 8.2 転送方式の選択が結果を左右しました

初回測定では 1k で PD分離が負けていましたが (0.90x)、原因は PD分離の原理的な限界ではなく転送実装でした。

- Python の `http.server` は Range 非対応で `sendfile` も使いません
- 単一 TCP フローは Wi-Fi の再送で輻輳ウィンドウが落ち、リンク容量の半分以下しか出ません

nginx へ変更し 8 並列 Range で取得することで、同じ Wi-Fi のまま転送が 3〜4 倍速くなりました (§5.4)。

**Wi-Fi 8 並列の 8.94x は、1GbE 推定の 10.12x に迫ります。** 10GbE を導入しなくても、転送の並列化だけで 1GbE 相当の効果がほぼ得られる計算です。10GbE の価値は、そこからさらに 3 倍強 (33.14x) を狙う部分にあります。

### 8.3 Decode は PD分離では改善しません

M1 の Decode は 19.0 → 7.0 tok/s とコンテキスト長に応じて劣化します。KV の読み出し量が増えるためで、Prefill をどこで行っても変わりません。

**PD分離が短縮するのは TTFT のみです。** 生成そのものは Decode 側の性能で決まります。16k で 32 トークン生成する場合、M1 では 4.4 秒かかります。

### 8.4 KV 量子化が最も効く転送削減策

転送量は KV 量子化に比例します ([01-research.md](01-research.md) §7)。

| KV 型 | 1 token | 16k のサイズ | 8 並列 (95 MiB/s) での転送 |
| --- | --- | --- | --- |
| f16 | 144 KiB | 2,304 MiB | 24 秒 |
| **q8_0 (採用)** | **76.5 KiB** | **1,196 MiB** | **13 秒** |
| q4_0 | 40.5 KiB | 648 MiB | 7 秒 |

q4_0 にすればさらに半減しますが、品質への影響は本 PoC では評価していません。

## 10. 10GbE 導入後にやること

1. `iperf3` で実効値を測り、[aggregate.py](../../scripts/pd/aggregate.py) の `NETWORKS["10gbe-est"]` を実測値へ差し替える
2. 構成 C の掃引を再実行する

```bash
CONNS=8 bash scripts/pd/sweep_pd.sh \
  "C-10gbe-8conn" \
  http://<4080のIP>:18080 http://127.0.0.1:18080 \
  http://<4080のIP>:18081 <Decode側の--slot-save-path> \
  1024 2048 4096 8192 16000
python3 scripts/pd/aggregate.py
```

3. 10GbE では RTT が下がるため、単一接続でも容量を使い切れる可能性があります。`CONNS=1` でも測って並列化の要否を確認してください

## 11. 残課題

- ~~KV 量子化 q4_0 での転送量削減~~ → [06-kv-quantization.md](06-kv-quantization.md) で検証済み。転送は 59〜60% に減り、16k の速度比は 4B で 8.94x → **13.76x** になりました。**品質への影響は未評価です**
- 32k 以上のコンテキストでの挙動 (M1 16GB のメモリ上限が制約になる)
- 転送の圧縮による短縮余地。KV は q8_0 の時点でエントロピーが高く、汎用圧縮の効果は限定的と予想されるが未検証
- 並列接続数の最適値。8 並列で 95.6 MiB/s に達しており、iperf3 の並列実測 (764 Mbps ≒ 91 MiB/s) を超えています。**リンク容量に張り付いているため、これ以上増やす余地はありません**
- ~~モデルサイズを変えたときの損益分岐の動き~~ → [05-model-scaling.md](05-model-scaling.md) で検証済み。16k の速度比は 4B の 8.94x に対し、8B で **12.66x**、14B で **19.69x** でした

### 検討して見送ったもの

**Prefill と転送のパイプライン化**は割に合いません。16,012 トークンで Prefill 1.9 秒に対し転送 12.5 秒であり、完全に重ね合わせても短縮は最大 1.9 秒 (12%) です。加えて llama-server の restore は `slot->prompt.clear()` を行うため、逐次的な restore を API 経由で行えません。実装コストに見合いません。
