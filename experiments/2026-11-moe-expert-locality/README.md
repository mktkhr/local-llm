# MoE の expert キャッシュはルーティングの局所性で効く(2026-11-moe-expert-locality)

llama.cpp 1.0 系の MoE cache(`-cmoe --moe-cache-mib N`)は、experts を RAM に置いたまま、よく使うものだけを VRAM に保持する。キャッシュが小さいとミスした expert を毎トークン PCIe で送ることになり、decode が遅くなる。ルーティングのトレース(`LLAMA_MOE_CACHE_TRACE`)を 1 本取れば、どのキャッシュサイズでも「何本ミスするか」は計算で出せるはずで、ミスのバイト数から速度も予測できるはずだ。LRU のスタック距離、人気度だけのモデル(Che 近似)、最適方式(Belady)、llama.cpp の実装の 4 つでヒット率曲線を出し、7 サイズの実測速度と突き合わせる。

## 結論

**decode の速度はミスのバイト数だけで決まり、ミスの数はトレース 1 本から計算できる。キャッシュが効くのは、連続するトークンが同じ expert を使い回すから(独立な選択の 3.3 倍)。**

7 サイズの実測は次の 1 本の直線に乗った(R² = 0.9995、誤差 0.16 ms 以内)。ミスのバイト数は、トレースを llama.cpp のキャッシュ実装(`moe-cache-tune.py` の複製)に通して数えた。

```
t(C) = 7.06 ms + (ミスした expert のバイト数 / トークン) / 10.6 GB/s
```

- **人気度だけではヒット率を半分近く見誤る。** expert の使用頻度だけから LRU を近似する Che 近似は、キャッシュ 19%(2 GiB)で 40% と予測するが、実際の LRU は 68%。連続する 2 トークンが同じ層で共有する expert は平均 2.36 本(8 本中)で、独立に選んだ場合の期待値 0.73 本の 3.3 倍ある
- **再参照の半分は 3 トークン以内。** LRU のスタック距離の中央値は 927 スロット(プールの 10%、約 3 トークン分の参照)、90% 点で 14 トークン分。直近数トークンの expert を持っているだけでヒットの大半が取れる
- **llama.cpp の方式は LRU より最大 5.5 ポイント良く(小さいキャッシュほど差が大きい)、最適方式との差はまだ大きい。** 2 GiB で LRU 67.5%、llama.cpp 71.0%、Belady 84.3%。ミスを Belady 並みにできれば、このサイズで 16.9 → 12.4 ms になる
- **RAM の experts を pinned にすると転送が 2.2 倍速い。** 既定(mmap)は 10.6 GB/s、`-lm none`(pinned)は 23〜24 GB/s(PCIe 4.0 x16 相当)。4 GiB のキャッシュで 11.4 → 8.9 ms。全 expert を pinned で持つ RAM が要るので、RAM を超えるモデル(Flash-Next など)には使えない
- **全 expert が入っても全部 VRAM より 0.8 ms 遅い。** 切片 7.06 ms に対し、`-cmoe` なしの全部 VRAM は 6.25 ms(2026-11-moe-decode-anatomy)。層ごとに選ばれた expert をホストへ読み出す同期(1 トークン 40 回)の分と考えられる
- 目安として、全部 VRAM の 1.5 倍(10.6 ms)に収めるには、mmap で約 4.6 GiB(experts の 42%)、pinned で約 2.6 GiB(24%)のキャッシュが要る

## なぜそうなるか

- **LRU のヒット率はスタック距離の分布そのもの。** 参照のたびに「前回の参照以降に使われた別の expert の数」(スタック距離 d)を数えると、容量 C の LRU は d < C のときだけヒットする(Mattson の包含性)。1 回の走査で全サイズのヒット率 H(C) = P(d < C) が出る
- **Che 近似が外れるのは、参照が独立ではないから。** Che 近似は「各 expert が人気度 p_k で独立に選ばれる」と仮定し、Σ(1 − e^{−p_k T}) = C を満たす特性時間 T からヒット率を出す。実際のルーティングは直前のトークンと同じ expert を選びやすく、短い間隔の再参照が多い。この分が LRU と Che の差(2 GiB で 28 ポイント)になる
- **局所性は層で違う。** 後半の層(30〜39)は共有本数 3.2 本と多いが、人気の偏りも強い(独立なら 1.1 本)。前半(0〜9)は共有 1.8 本で独立なら 0.47 本、比は前半のほうが大きい(層 2 で 5.3 倍)。最初の層 0 だけは 1.5 倍とほぼ独立
- **速度がミスのバイト数に比例するのは、転送が直列で、ヒットの計算はキャッシュの大きさに依らないから。** ミスした expert は 1 本ずつ PCIe で送られ、送り終わるまでその層の計算が待つ。ヒットした expert の計算量は全部入りのときと同じなので、切片は一定になる
- **mmap の experts は転送が遅い。** ページキャッシュ上の通常のメモリからは、ドライバが一度 pinned の中継バッファへ写してから送る。`-lm none` で最初から pinned に読み込むとこの写しが無くなる

## 計測条件

- モデル: unsloth `Qwen3.6-35B-A3B-UD-IQ3_S`(256 experts、k=8、40 層)。キャッシュ上のグループは 2 つ(37 層は 1 expert 1.12 MB、3 層は 1.23 MB)。全 expert を入れる最小サイズは 11,054 MiB
- サーバ: `-ngl 99 -cmoe --moe-cache-mib C --flash-attn on -np 1 -c 16384 -ctk q8_0 -ctv q8_0 -b 2048 -ub 512 --no-mmproj`、C = 1024 / 2048 / 3072 / 4096 / 6144 / 8192 / 11100 MiB。pinned は `-lm none` を足して 4096 と 2048 で測った
- 生成: 2026-11-greedy-divergence のプロンプト 17 本(コード書き換え 14 本と推論 3 本)を、`/completion` で `temperature: 0`、400 トークンずつ順に流す。速度は全リクエストの `predicted_ms` の合計 / 生成トークン数(最初のリクエストのキャッシュの埋まり込み)
- トレース: キャッシュを通る(32 トークン以下のバッチの)ルックアップをすべて記録する。6,864 トークン、参照 2,184,078 回。キャッシュはグループ内の全層で 1 つのプールを共有するので、参照列はグループごとに層をまたいだ時刻順に並べた。1 ルックアップ内の重複は 1 回に数えた
- 各方式のヒット率は、llama.cpp がそのサイズで確保するスロット数(`n_slots_of`)で計算した。llama.cpp の方式は `scripts/moe-cache-tune.py` の `ClassLRU`(使用頻度を半減期 128 トークンで減衰させたクラス別の LRU)。b12464 の版を `git show d3c3e242c:scripts/moe-cache-tune.py` で取り出して使った
- 7 サイズとも生成トークン列は完全に一致した(キャッシュの有無は数値を変えない)

## 次

- Belady との差(2 GiB でミス 29% vs 16%)は、次のトークンの expert を当てられれば縮められる。「直前のトークンの expert を残す」以上の予測(層 l の選択から層 l+1 を当てる、など)がどこまで効くかをトレースで試算できる
- このトレースと時間モデルがあれば、VRAM に入らないモデル(Flash-Next など)でも 1 回の実行から最適なキャッシュサイズを計算できる。ただし Flash-Next は RAM 32 GB では pinned にできず、SSD からの読み出しが別の律速になる(2026-11-flash-next-moe-cache)
