# Claude Code の 1 ターンは何に固定費を払っているか(2026-11-cc-turn-overhead)

Claude Code は毎ターン、system プロンプト・ツール定義・会話履歴の全部を `/v1/messages` に送り直す。プレフィックスはキャッシュに乗るので prefill はほぼ新しい部分だけで済むが、それでも 1 ターンごとに「全文を受け取って整形し、トークンに直し、キャッシュと照合する」仕事が残る。同じ本文を再送したとき(新しいトークンが 0 のとき)の所要時間をこのターンの固定費と見て、ツール数と会話の長さで振り、部品に分ける。あわせて llama.cpp build 12182 と 12464(1.0 系)を比べる。

## 結論

**10 万トークン級の Claude Code リクエストは、新しいトークンが 0 でも 1 ターン約 0.3 秒かかる。その半分以上はプロンプト全文のトークナイズで、次が GDN 状態の checkpoint の作り直し(毎回 38 ms)。**

再送 1 回の時間は、プロンプトのトークン数 n(千トークン単位)でほぼ直線になる(build 12464、11 条件、R² = 0.99)。

```
t_warm ≈ 57 ms + 2.56 ms × n
```

ツール 137 個(84,880 トークン)の再送 295 ms の内訳(build 12464)。

| 部品                                        | 時間       | 割合 | 測り方                                                  |
| ------------------------------------------- | ---------- | ---- | ------------------------------------------------------- |
| トークナイズ(1.82 µs / トークン)            | **148 ms** | 50%  | `count_tokens` − `apply-template`                       |
| jinja テンプレート + grammar 文字列         | 58 ms      | 20%  | `/apply-template`(うち grammar 文字列 14 ms)            |
| checkpoint の作り直し(62.8 MiB、VRAM → RAM) | **38 ms**  | 13%  | ログの `superseding` → `created`                        |
| grammar のパースとサンプラ構築              | 16 ms      | 5%   | ログのスロット選択 → タスク開始(ツール 0 個では 0.1 ms) |
| 末尾 4 トークンの評価とサンプリング         | 16 ms      | 5%   | ログ                                                    |
| サンプラへのプロンプト投入                  | 10 ms      | 3%   | ログの `init sampler`(0.12 µs / トークン)               |
| checkpoint の復元(62.8 MiB、RAM → VRAM)     | 6 ms       | 2%   | ログ                                                    |
| 応答の組み立てと HTTP                       | 3 ms       | 1%   |                                                         |

- **トークナイズが最大の固定費。** キャッシュ照合はトークン列で行うので、変わっていない 10 万トークンも毎ターン全部トークナイズし直している。1 トークン 1.82 µs(約 55 万トークン / 秒)は、prefill に換算すると 800 トークン分に相当する
- **checkpoint の作り直しは長さに依らず 38 ms。** Qwen3.6 は GDN(再帰状態を持つ層)が混ざる hybrid モデルなので、末尾 4 トークンを評価し直すために 4 トークン手前の状態(62.8 MiB)を毎回 VRAM からホストへ写す。再送で中身が同じでも「同じ位置の checkpoint を置き換える」処理が走る。逆向きの復元は 6 ms で済むので、写し方(確保し直しや小分けのコピー)に 30 ms 前後の無駄がある可能性がある
- **grammar のコストは前処理だけで、生成中はほぼゼロ。** ツール 137 個で grammar 文字列 14 ms + パース 16 ms。tool_call を出す条件でも、生成 1 トークンあたりの上乗せは 0.03〜0.15 ms(1% 未満)。llama.cpp の grammar は、モデルが選んだトークンが文法に合っていれば全語彙を調べ直さないので、素直に tool_call を書くモデルでは安い
- **llama.cpp 1.0 系で jinja が 2.9 倍速くなった。** 会話 1 文字あたりのテンプレート時間は 0.245 → 0.085 µs(103 メッセージで 83 → 38 ms)。再送 1 回は 374 → 328 ms(−12%)。トークナイズと checkpoint は変わらない
- **`tool_choice: any` は呼び出しを強制しない。** llama.cpp の required は「本文 → tool_call」の順を許す文法なので、上限トークン内では本文だけ返ることがある(96 トークンでは auto と同じ出力)
- **本番構成の `--cache-reuse 256` は無効になっている。** hybrid モデルでは起動時に `cache_reuse is not supported by this context, it will be disabled` が出て、オプションは黙って外れる。10 月実験のターン間ヒット率は、プレフィックス一致と checkpoint によるもの

## なぜそうなるか

- **固定費が n に比例するのは、前処理が全文を毎回なめるから。** HTTP で受けた JSON のパース、Anthropic 形式から OpenAI 形式への変換、jinja でのプロンプト生成、トークナイズ、サンプラへの投入は、どれもキャッシュの有無に関係なく全文に対して走る。傾き 2.56 ms / 千トークンのうち 1.82 がトークナイズ、残りがテンプレートとサンプラ投入
- **切片の 57 ms は checkpoint の往復と最小の評価。** 作り直し 38 ms + 復元 6 ms + 末尾 4 トークンの評価 9 ms で 53 ms。純粋な Transformer なら KV キャッシュの末尾を 1 トークン消すだけで済む処理が、再帰状態を持つ GDN では状態の丸ごとの保存と復元になる
- **新しいトークンがあるターンでは、ここに prefill が足される。** prefill は 1 万トークンで約 5,300 トークン / 秒なので、1 ターンに 1,000 トークン増えるなら prefill 約 0.2〜0.3 秒(文脈が長いほど遅い)+ 固定費 0.3 秒になり、固定費のほうが大きい。ツール結果が短い往復ほど固定費が効く

## 計測条件

- モデル: unsloth `Qwen3.6-35B-A3B-UD-IQ3_S`(全部 VRAM)
- サーバ: 本番の C 構成に合わせた `--jinja -ngl 99 --flash-attn on -np 1 -c 131072 --kv-unified -ctk q8_0 -ctv q8_0 -b 2048 -ub 512 --cache-reuse 256 --no-mmproj --metrics`(`--cache-reuse` は上記のとおり無効化される)
- リクエスト: 10 月実験で ccshim のログから抜いた Claude Code の実リクエスト(リポジトリには入れない)。ツール軸は W1-02(137 ツール、3 メッセージ)のツールを先頭から 0 / 8 / 16 / 33 / 64 / 137 個に切った。会話軸は W1-03(33 ツール、103 メッセージ)の会話を、ユーザー発話で終わる 1 / 9 / 25 / 49 / 103 件に切った
- build に依存する欄を揃えるため、`metadata`、`context_management`、`output_config`(12464 だけが `reasoning_effort` に変換する)を外し、`thinking` は無効、`temperature: 0`、`max_tokens: 1` に固定した
- 1 条件で叩くもの(各 5 回、中央値)
  - `GET /health`: HTTP の往復。以降の値からこれを引く
  - `/apply-template`(OpenAI 形式): パース + jinja + grammar 文字列。`tool_choice: none` 版も叩き、差を grammar 文字列とする(同じプロンプトになることを文字数で確認)
  - `/tokenize`: 整形済みプロンプトのトークナイズ
  - `/v1/messages/count_tokens`: 本番と同じ前処理(変換 + テンプレート + トークナイズ)。トークン数が `/tokenize` と一致することで、Python 側の Anthropic → OpenAI 変換がサーバと同じであることを確かめた(全 22 条件で一致)
  - `/v1/messages` の初回と再送、`/v1/chat/completions` の再送、`tool_choice: any` の再送、96 トークンの生成(auto / none / any)
- スロット内部の分解: build 12464 を `-lv 4` で起動し、ツール 0 個と 137 個を 4 回ずつ再送して、ログのタイムスタンプから区間を切った(`scripts/trace_parse.py`)

## 落とし穴

| 罠                                                               | 症状                                                                     | 対処                                                                                 |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `/metrics` の prompt 秒数はスロットの処理時間ではない            | 再送の prompt_seconds は 9 ms なのに、ログの `prompt eval time` は 55 ms | `/metrics` は GPU の計算だけを数える。checkpoint の往復はログ(`-lv 4`)でしか見えない |
| `tool_choice: any` で本文が返る                                  | `tool_use` ではなく `text` ブロック                                      | 仕様。llama.cpp の required は呼び出し前の本文を許す                                 |
| `--cache-reuse` が黙って無効になる                               | 起動ログに 1 行警告が出るだけ                                            | hybrid モデルでは効かない前提で考える                                                |
| 12464 は `output_config.effort` を `reasoning_effort` に変換する | Claude Code の本文をそのまま送ると build 間でプロンプトが変わりうる      | 計測では `output_config` を外して揃えた                                              |
| プロンプトを切り替えると RAM のプロンプトキャッシュへ退避が走る  | 1 万トークン(426 MiB)の退避に 88 ms                                      | `-np 1` でサブエージェントと本体が交互に来ると毎回払う。今回の計測には含めていない   |

## 次

- トークナイズの 150〜200 ms は、プレフィックスが同じなら前回のトークン列を使い回せば消せる(サーバ側の差分トークナイズ、または ccshim でのトークン列キャッシュ)。llama.cpp に同種の提案があるか調べる
- checkpoint の作り直し 38 ms と復元 6 ms の非対称の原因(ピン留めメモリの有無、確保し直し)をソースで確認する
- 実際の Claude Code セッションでは、ターンごとの新トークン数と、サブエージェントによるプロンプト切り替えの頻度で固定費の比率が決まる。ccshim のログから両方を数えれば、セッション全体でこの固定費が何秒になるかを出せる
