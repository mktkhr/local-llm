# 階層型 KV キャッシュ — Phase 3〜5: 実測結果 (Track 0 / llama.cpp)

VRAM / DRAM / SATA SSD の 3 階層から KV を復元し、再 Prefill と比較した記録です。

- 実施日: 2026-09-03
- 結果: **H1 / H2 / H3 / H5 成立。H4 は未検証**
- 設計: [02-design.md](02-design.md) / 調査: [01-research.md](01-research.md)

## 1. 結論

1. **200,000 tokens で、full prefill 141.6 秒が DRAM から 1.6 秒 (89.6x) / SSD から 20.2 秒 (7.0x) になりました。** 本 PoC の主目的である「長 context セッションの再開」は成立します (H3 成立)。
2. **DRAM tier は全長・全 KV 型で再 Prefill より速い (H1 成立)。** 損益分岐は存在しません。
3. **SSD tier (SATA) の損益分岐は KV 量子化で 1 桁動きます (H5 成立)。** f16 で約 10 万、q8_0 で 43,429、q4_0 で 10,633 tokens。**KV 量子化が SSD tier 成立の主レバー**であることが実測で確定しました。
4. **事前予測 ([01-research.md](01-research.md) §5) は q8_0 で誤差 6%、q4_0 で 11%** でした。1k〜16k のデータから 200k までの外挿が成立しています。
5. **階層には帯域だけでなく容量の壁があります。** DRAM に載り切らないサイズになった瞬間、実測値が SSD 速度へ落ちました (§6.1)。単純な「速度表」では設計できません。

### 3.4 実効帯域

| 経路                              | 実効帯域                                                               |
| --------------------------------- | ---------------------------------------------------------------------- |
| SSD → VRAM (Case D)               | **391〜393 MiB/s** (17 構成中 15 構成)。O_DIRECT 実測 377 MiB/s と整合 |
| DRAM page cache → VRAM (Case Dw)  | **4,150〜7,300 MiB/s**                                                 |
| DRAM prompt cache → VRAM (Case C) | **5,400〜5,600 MiB/s**                                                 |

**DRAM 経路は PCIe Gen4 x16 の実力 (20 GB/s 級) の 1/4 程度**にとどまります。`llama-context.cpp` の `write_tensor` / `read_tensor` が一時バッファを経由するため、GPU ↔ host が 1 回の DMA で済んでいません。**ここに 4〜5 倍の伸びしろがあります。** SGLang HiCache の `page_first_direct` レイアウトや pinned memory はまさにこの部分を狙った最適化です。

例外は 2 点で、いずれも直前に 11 GiB 級の書き込みを行った後の読み出しでした (f16 78k: 279 MiB/s、q8_0 150k: 366 MiB/s)。DRAM-less の BX500 で SLC キャッシュが枯渇した挙動と整合します。**事前の 6 GiB 書き込みテストでは顕在化しなかった劣化が、11 GiB 規模で現れました** ([01-research.md](01-research.md) §9-8 の懸念が的中)。

## 4. 損益分岐

`results/kvtier_breakeven.csv`。full prefill は N の 2 次、復元は N に線形なので、両者は必ず 1 点で交わります。

| KV 型    | KV/token  | SSD 復元コスト | **損益分岐 (実測)** | 事前予測 | 誤差       |
| -------- | --------- | -------------- | ------------------- | -------- | ---------- |
| f16      | 144.0 KiB | 0.52195 ms/tok | 162,861 tokens ※    | 111,000  | +47%       |
| **q8_0** | 76.5 KiB  | 0.20298 ms/tok | **43,429 tokens**   | 46,000   | **−5.6%**  |
| **q4_0** | 40.5 KiB  | 0.10128 ms/tok | **10,633 tokens**   | 12,000   | **−11.4%** |

※ f16 の値は §3.4 の 78k 点 (279 MiB/s) に引きずられています。SSD が 393 MiB/s を維持した場合の理論値は、実測した f16 の prefill 曲線から **約 99,000 tokens** です。

**DRAM tier (prompt cache) は全 KV 型で損益分岐なし** — どの長さでも復元が有利です。

### 4.1 事前予測との突き合わせ

[01-research.md](01-research.md) §5 は既存 PD分離 PoC の **1k〜16k** 実測からの外挿でした。今回 **10k〜200k** で検証しています。

| 項目                  | 事前予測        | 実測 (q8_0)      | 誤差  |
| --------------------- | --------------- | ---------------- | ----- |
| prefill 係数 a        | 0.0758 ms/tok   | 0.0728 ms/tok    | −4.0% |
| prefill 係数 b        | 2.84e-6 ms/tok² | 3.110e-6 ms/tok² | +9.5% |
| SSD 復元コスト (q8_0) | 0.208 ms/tok    | 0.20298 ms/tok   | −2.4% |
| 100k の full prefill  | 36.0 s          | 38.9 s           | +8.1% |
| 200k の full prefill  | 128.8 s         | 141.6 s          | +9.9% |

**12 倍の外挿区間でも 10% 以内で当たりました。**

### 4.2 KV 量子化は prefill を少し遅くする

| tokens | f16        | q8_0                | q4_0                |
| ------ | ---------- | ------------------- | ------------------- |
| 10,000 | 984.5 ms   | 1,042.6 ms (+5.9%)  | 1,030.3 ms (+4.7%)  |
| 48,000 | 9,893.2 ms | 10,680.7 ms (+8.0%) | 10,530.2 ms (+6.4%) |

**量子化 KV は prefill / decode を 5〜8% 遅くする代わりに、復元を 2〜4 倍速くします。** 復元頻度が高い用途では明確に得です。

## 5. decode 速度は階層化では改善しない

| tokens              | 10,000 | 25,000 | 48,000 | 100,000 | 200,000  |
| ------------------- | ------ | ------ | ------ | ------- | -------- |
| decode tok/s (q4_0) | 128.5  | 99.0   | 68.9   | 40.7    | **22.4** |

**KV を瞬時に復元できても、その後の生成は 200k で 22.4 tok/s まで落ちます。** 復元が短縮するのは TTFT だけで、生成速度は KV の読み出し量に支配されます。既存 PD分離 PoC の結論 ([2026-08-pd-split/notes/04-results.md](../../2026-08-pd-split/notes/04-results.md) §8.3) と同じです。

200k のセッションで 200 トークン生成する場合、TTFT 1.6 秒 + 生成 8.9 秒 になります。**階層化しても「長い context は生成が遅い」という性質は残ります。**

## 6. 階層には容量の壁がある

帯域だけを見て設計すると外します。実測で 2 度それが現れました。

### 6.1 DRAM に載り切らないと、ファイル経路は SSD 速度へ落ちる

q8_0 150k の Case Dw (page cache 経由) だけ **28,452 ms** で、SSD (30,605 ms) とほとんど変わりませんでした。

|                 | q8_0 100k              | q8_0 150k                 |
| --------------- | ---------------------- | ------------------------- |
| KV サイズ       | 7,473 MiB              | 11,209 MiB                |
| C: prompt cache | 1,556 ms (4,802 MiB/s) | 2,216 ms (5,059 MiB/s)    |
| Dw: page cache  | 1,756 ms (4,257 MiB/s) | **28,452 ms (394 MiB/s)** |

原因は容量です。DRAM 24 GiB のうち prompt cache が 14 GiB を確保しているため、11.2 GiB のファイルを page cache に保持しきれず、実際にディスクから読み直しています。

**Dw は「DRAM tier の性能」ではなく「ファイルがまだ page cache に残っていれば速い」という条件付きの値です。** 一方 C (prompt cache) は明示的に確保した領域なので、容量内であれば安定して 5 GiB/s 級を出します。

**tier を設計するなら、OS 任せの page cache ではなく明示的に確保した領域を使うべき**、という実測上の裏付けになります。

### 6.2 page cache を落とさないと Case D は Case C になる

| KV 型 / tokens | 落とす (D)  | 落とさない (Dw) | 差        |
| -------------- | ----------- | --------------- | --------- |
| q4_0 10,000    | 1,007.5 ms  | 56.7 ms         | **17.8x** |
| q8_0 10,000    | 1,901.8 ms  | 106.9 ms        | **17.8x** |
| q4_0 200,000   | 20,248.6 ms | 1,883.7 ms      | **10.7x** |

`posix_fadvise(POSIX_FADV_DONTNEED)` で対象ファイルだけ落としています (root 権限不要)。

## 7. Case E: partial prefix reuse

prefix を共有し tail だけ差し替えた場合、**再計算されるのは差分の 244 トークンだけ**でした。

| tokens (q4_0) | 再 Prefill | prefill 時間 | full prefill 比 |
| ------------- | ---------- | ------------ | --------------- |
| 10,000        | 244        | 42.3 ms      | 24.4x           |
| 100,000       | 244        | 208.8 ms     | 183.6x          |
| 200,000       | 244        | 394.7 ms     | **358.8x**      |

ただし **244 トークンしか計算していないのに、context が長いほど時間が増えます** (42.3 → 394.7 ms)。新しいトークンが既存の全 KV にアテンションを張るためで、これは削れません。**partial prefix reuse にも「context 長に比例する下限コスト」が残ります。**

## 8. 計測手法上の発見: mincore() は他人のファイルの page cache 状態を隠す

Case D の検証に `mincore()` を使ったところ、**KV ファイルが root 所有 (コンテナが書いたもの) のとき、実際には cold なのに「全ページ常駐」と報告されました**。

Linux 5.0 の CVE-2019-5489 対策 (`mm/mincore.c` をより保守的にする変更) により、**呼び出し側がそのファイルへの書き込み権限を持たない場合、mincore は page cache の実状態を隠します**。

対策として [config/compose.yml](../config/compose.yml) に `user: "${KVT_UID}:${KVT_GID}"` を追加し、KV ファイルを host ユーザ所有で書かせています。修正後は `748.3 MiB → 0.0 MiB` と正しく検証できました。

なお計測値そのものは修正前後で変わっていません (10k q8_0: 1,902.4 ms → 1,901.8 ms)。**壊れていたのは計器であって測定対象ではありませんでした**が、制御実験をするまでそれは分かりませんでした。

## 10. 残課題

1. **マルチセッション (H4)** — 唯一未判定の仮説。prompt cache 14 GiB に何セッション入るか、L3 が hit ratio をどれだけ押し上げるか
2. **復元経路の最適化余地** — 実効 4〜5 GiB/s は PCIe Gen4 の 1/4。pinned memory / 一時バッファ除去でどこまで詰められるか (§3.4)
3. **q4_0 の品質評価** — 損益分岐を 10,633 まで下げる最大のレバーだが、品質は未評価。[docs/evaluation.md](../../../docs/evaluation.md) の採点系で測れる
4. **明示確保 tier と page cache の使い分け** — §6.1 の設計含意を、L3 を持つ実装 (SGLang HiCache) で検証する
5. **Track 1 (SGLang HiCache)** — page 単位の partial hit、write policy 3 種の比較
6. **BX500 の SLC キャッシュ枯渇** — 11 GiB 級の書き込みで再現。掃引順序による測定バイアスの調査
