# llama.cpp (llama-swap) による Claude Code バックエンド

RTX 4080 SUPER (16GB) 上で **Qwen3.6-35B-A3B** を動かし、Claude Code のバックエンドとして使うための構成と実測記録。

## 結論

**採用: `qwen36-35b-iq4xs`(UD-IQ4_XS / `--n-cpu-moe 10` / ctx 131,072 / KV q8_0)**

3 つの量子化を同一条件で比較し、実タスクの総所要時間が最短だった構成。

| 構成        | 量子化     | ncmoe | VRAM 実測  | 実タスク 4 課題          | 合計時間   |
| ----------- | ---------- | ----- | ---------- | ------------------------ | ---------- |
| **B(採用)** | UD-IQ4_XS  | 10    | 15,329 MiB | **4/4 PASS**             | **9.4 分** |
| C           | UD-IQ3_S   | 0     | 15,032 MiB | 4/4 PASS                 | 14.6 分    |
| A           | UD-Q4_K_XL | 17    | 15,358 MiB | 3/4(React/TS で時間切れ) | 28.9 分    |

## 1. 構成

```
別 PC の Claude Code
   ↓ ANTHROPIC_BASE_URL
ccshim (:11436)          ← messages 内の role:"system" をトップレベルに畳み込む
   ↓
llama-swap (:11435)      ← model 名を見てモデルを入れ替える
   ↓
llama-server             ← llama.cpp b10438 / CUDA 12.8
```

`docker compose up -d` で両方が起動する。`restart: unless-stopped`。

### ccshim が必須である理由

Claude Code は **トップレベル `system` とは別に、`messages` 配列へ `role:"system"` のメッセージを注入**する(中身は Agent タイプ一覧)。Qwen 系の Jinja チャットテンプレートはこれを

```
raise_exception('System message must be at the beginning')
```

で拒否するため、**llama-server は全リクエストに 500 を返す**。最小再現も確認済みで、`messages` に `role:"system"` が 1 つでもあれば位置に関係なく失敗する。ccshim はこれをトップレベル `system` の末尾ブロックに移すだけで、内容は失われない。

**SSE は逐次転送しなければならない。** バッファすると thinking が長いときにクライアントから無応答の接続に見え、アイドルタイムアウトで再送が多重化して破綻する(実測: thinking 26,000 トークンで 282 秒ごとに再送、待ち行列が 502→680→842→1,004 秒と膨張)。

### なぜ Docker で公開するか

ホストのプロセスとして動かすと ufw(`DEFAULT_INPUT_POLICY=DROP`)に阻まれて LAN から届かない。Docker の publish は iptables の `DOCKER` チェーンに入るため **ufw の設定変更なしで LAN に出せる**。llama-swap (:11435) が最初から届いていたのはこのため。

## 2. クライアント設定(別 PC)

`zshrc-snippet.sh` を `~/.zshrc` から `source` する。

```bash
ccb          # B(UD-IQ4_XS)で起動 ← 推奨
ccc          # C(UD-IQ3_S)で起動
ccd          # D(UD-IQ3_S、256k・KV q4_0)で起動。長文コンテキストが必要なときのみ(section 12 参照)
ccstat       # ロード中のモデルを表示
```

手動で起動する場合:

```bash
ANTHROPIC_BASE_URL=http://192.168.0.144:11436 \
ANTHROPIC_API_KEY=dummy \
ANTHROPIC_AUTH_TOKEN=dummy \
ANTHROPIC_MODEL=qwen36-35b-iq4xs \
API_TIMEOUT_MS=1800000 \
CLAUDE_CODE_MAX_CONTEXT_TOKENS=131072 \
claude
```

| 設定                                                 | 理由                                                                                               |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| ポート **11436**(shim)                               | 11435 に直結すると全リクエストが 500 になる                                                        |
| `ANTHROPIC_API_KEY` と `ANTHROPIC_AUTH_TOKEN` の両方 | どちらのヘッダが使われるかはバージョン依存                                                         |
| `ANTHROPIC_MODEL`                                    | 未設定だと Claude Code の既定名が送られ 404。`claude-opus-5` / `claude-sonnet-5` は alias 登録済み |
| `API_TIMEOUT_MS`                                     | 既定 600 秒。thinking が伸びると 1 リクエストが 500 秒を超える                                     |
| `CLAUDE_CODE_MAX_CONTEXT_TOKENS`                     | 未知のモデル名だと **200k と誤認**する。実際は 131,072                                             |
| 起動前のウォームアップ                               | モデル切替中に `/v1/messages` を叩くと connection reset で切られる                                 |

**claude-code-router は不要かつ有害。** llama-server が `/v1/messages` をネイティブ実装しているため変換層は要らない。router は使えるエンドポイントを探して `model` 無しの探索リクエストを撃つため、llama-swap が全部 404 を返し認証エラーとして表面化する。

## 4. モデル構造(V-1)

```
llama_kv_cache: size = 1360.00 MiB (131072 cells, 10 layers, 1/1 seqs), K (q8_0): 680.00 MiB, V (q8_0): 680.00 MiB
llama_memory_recurrent: size = 62.81 MiB (1 cells, 40 layers)
```

**128k / q8_0 の KV はわずか 1,360 MiB。** GDN ハイブリッドであることが実測で確認できた。

- `n_layer = 40` に対し **KV を持つのは 10 層のみ**(`full_attention_interval = 4`)
- 残り 30 層は線形(SSM/GDN)で、状態は文脈長に比例せず **62.81 MiB 固定**
- `n_head_kv = 2`、`n_embd_k_gqa = n_embd_v_gqa = 512`、`n_swa = 0`
- MoE: `expert_count = 256` / `expert_used_count = 8`(活性 3B)

検算: 10 層 × (512+512) × 1.0625 B × 131,072 = 1,360 MiB(ログと完全一致)

**このモデルは VL(マルチモーダル)**。`--no-mmproj` を付けないと `mmproj-BF16.gguf`(0.9 GB)を自動ロードして VRAM を無駄に消費する。

## 5. `--n-cpu-moe` の確定(Step 1)

15.5 GB 以下に収まる最小の N。1 秒間隔で `nvidia-smi` を採取し、実推論を 1 本流してピークを踏ませた値。

| 構成 | 重み       | 確定 ncmoe | VRAM 実測 | compute buffer | 1 層あたり | CPU へ逃がす量 |
| ---- | ---------- | ---------- | --------- | -------------- | ---------- | -------------- |
| A    | 21,325 MiB | **17**     | 15,358    | 585            | 463 MiB    | 約 8.0 GB      |
| B    | 16,910 MiB | **10**     | 15,329    | 545            | 356 MiB    | 約 3.4 GB      |
| C    | 13,033 MiB | **0**      | 15,032    | 436            | 275 MiB    | なし           |

境界は実測で挟み込んだ(A: N=16 で 15,822 超過 / N=14 で OOM、B: N=8 で OOM)。KV は 3 構成とも 1,360 MiB で一定。

## 6. 速度(Step 2)

`llama-bench -p 30720 -n 128 -d 0,30720,131072 -r 3`。スロットリングは全測定で未発生。

| 指標               | 基準点 9B Q8_0 | **C** IQ3_S  | **B** IQ4_XS | **A** Q4_K_XL |
| ------------------ | -------------- | ------------ | ------------ | ------------- |
| モデル実体         | 8.86 GiB       | 12.73 GiB    | 16.50 GiB    | 20.81 GiB     |
| `pp30720`          | 5,789.07       | **4,357.68** | 1,388.48     | 798.81        |
| `tg128 @ d=0`      | 68.69          | **153.14**   | 74.78        | 66.77         |
| `tg128 @ d=30720`  | 64.00          | **130.32**   | 68.68        | 62.10         |
| `tg128 @ d=131072` | 51.76          | **83.42**    | 51.47        | 48.95         |

**CPU オフロードはプレフィルを直撃し、生成にはほとんど効かない。**

- pp は 4,358 → 1,388 → 799 と激減(オフロード 0 → 10 → 17 層)
- tg は 130 → 69 → 62 に留まる

理由は MoE の構造。1 トークンあたり 256 エキスパート中 8 個しか活性化しないため、層を CPU に逃がしても実際に読むバイト数は少なく、帯域律速になりにくい。一方プレフィルはバッチ全体の演算量が効くため、**AVX-512 を持たない Ryzen 5 3600 の演算能力がそのまま出る**。

## 9. Ollama との比較(2026-08-16)

移行前に「tool use なら llama.cpp のほうがよい」という前提を検証したが、**再現しなかった。**

`gpt-oss:20b` / `qwen3.5:9b` / `gemma4:12b-it-qat` の 3 モデルで、ツール 4 件・12 件 + ネストスキーマ・逐次チェーン・並列 tool call・過剰発火の 7 項目を同一機体で比較。**全項目で両ランタイムとも通過。** Anthropic の `/v1/messages` も両者が実装しており、`thinking` + `tool_use` ブロックを正しく返す。

参照した不具合報告([ollama#14601](https://github.com/ollama/ollama/issues/14601)、[#14745](https://github.com/ollama/ollama/issues/14745)、[#11704](https://github.com/ollama/ollama/issues/11704))の多くは Ollama 0.24〜0.25 系のもので、0.32.9 では修正済みと見られる。

llama.cpp を選ぶ実利は tool call 品質ではなく、**モデルごとに `--n-cpu-moe` / KV 量子化 / batch を個別指定できる運用自由度**にある。今回の測定はまさにそれを前提としている。

## 10. 落とし穴

| 事象                              | 原因 / 対処                                                                                    |
| --------------------------------- | ---------------------------------------------------------------------------------------------- |
| 全リクエストが 500                | Claude Code の `messages` 内 `role:"system"`。**ccshim 必須**                                  |
| thinking が長いと再送が多重化     | シムが SSE をバッファしていた。**逐次転送にする**                                              |
| LAN から届かない                  | ufw が `DROP`。**Docker で publish する**(ufw を迂回)                                          |
| `no model id could be identified` | ボディが JSON として解釈されていない。**`Content-Type: application/json` を付ける**            |
| `no router for requested model`   | `ANTHROPIC_MODEL` 未設定、またはモデル名の誤り(`qwen3.6-` ではなく **`qwen36-`**)              |
| コンテキスト超過                  | Claude Code が 200k と誤認。**`CLAUDE_CODE_MAX_CONTEXT_TOKENS=131072`**                        |
| モデル切替直後に connection reset | ロード中の `/v1/messages` は待たずに切られる。**先に `/v1/chat/completions` でウォームアップ** |
| VRAM 測定が壊れる                 | llama-swap は `ttl` 未指定で常駐する。**計測前に停止する**                                     |
| `-ctk q4_0`                       | 公式が tool calling 品質を有意に落とすと明記。**q8_0 まで**                                    |

## 11. 測定上の訂正と限界

記録として残す。

1. **「B が SQL のバグを発見した」は誤り。** `$1` が 3 箇所で使われるのは正しく、`$3` に閾値も正しく渡っている。B の指摘は誤読(偽陽性)だった。元コミットに対して検証済み
2. **T2(バグ発見課題)には正解が存在しなかった。** 対象リポジトリに明白な実バグがなく、判別テストとして成立していなかった。私が監査して見つけた 2 件(`EMBEDDING_DIMENSION` が未使用、IVFFlat を空テーブルに作成)は専門知識寄りで、日常業務の想定に対して過剰だったため課題ごと差し替えた
3. **A/M3 を当初 PASS と誤判定。** 時間切れかつ変更 0 件だったが、素のツリーでもビルドが通るため合格と誤認。「変更 0 件は FAIL」「`timeout`(exit=124)は FAIL」を条件に追加して訂正
4. **greedy でも実行間のばらつきは消えない。** 同一設定の T1 が 44.30 秒と 56.0 秒。Claude Code が送るプロンプトにセッションごとに変わる要素があるため、計画の「greedy で分散を消す」という前提は成立していない
5. **各課題 n=1。** 量子化間の差は 1 サンプルの観測であり、特に M3 の A の失敗が恒常的かは未確認

### 未検証

- ツール定義を減らす方法(MCP 無効化等)でプレフィルを削減できるか。プロンプトの 87% がツール定義なので効果は大きいはず
- 2 セッション同時利用(現状 `-np 1` で 1 スロット)
- gpt-oss-20b / Qwen3.5-9B との実タスク比較(Step 4 相当)

## 12. 256k 化(`ccd`)の検証(2026-08-22)

`ccc`(C 構成、ctx=131,072)を単純に `--ctx-size 262144` にすると、section 4 の検算通り KV が 1,360→2,720 MiB に倍増し、重み 13,033 MiB + KV 2,720 MiB + バッファ(~400〜600)でほぼ 16,000〜16,200 MiB になり、GPU 総容量 16,376 MiB からデスクトップ常駐分(Xorg 等 ~190〜300 MiB)を引くと溢れる計算だった。KV 量子化を落とさず(既存方針: q4_0 は tool calling 品質を有意に落とすため避ける)256k を収める案と、方針に反してでも q4_0 にする案の 2 通りを実際に立てて比較した。

一時検証エントリを `config.yaml` に追加(**未コミット**。本採用が決まったら正式名にリネームする):

- `qwen36-35b-iq3s-256k-q8`(D-A): `-ctk/-ctv q8_0` 維持、`--n-cpu-moe` で重みを CPU に逃がして VRAM を確保
- `qwen36-35b-iq3s-256k-q4`(D-B): オフロードなし(フル GPU)、`-ctk/-ctv q4_0`

### ncmoe の確定(D-A)

section 5 と同じ手法(モデルロード直後の VRAM ピークを nvidia-smi で採取)。

| ncmoe | VRAM 実測  | 余裕(総容量比) | 判定                                     |
| ----- | ---------- | --------------- | ----------------------------------------- |
| 4     | 15,787 MiB | 589 MiB         | 既存構成(~1,000 MiB 前後)より薄く、見送り |
| **6** | **15,240 MiB** | **1,136 MiB** | 既存構成と同等の余裕。**採用**            |

D-B(オフロードなし、q4_0)は 15,521 MiB、余裕 855 MiB で既存構成と同水準。

### 速度比較

同一プロンプト(`prompt_n=18,024`)を両構成に投げた簡易計測(`llama-bench` ではなく `/v1/chat/completions` の `timings` を使用。深さは 18k 止まりで 256k 全域はカバーしていない)。

| 指標                 | D-A(q8_0 + ncmoe6) | D-B(q4_0・オフロードなし) |
| -------------------- | ------------------- | -------------------------- |
| VRAM                 | 15,240 MiB           | 15,521 MiB                  |
| prompt (pp) t/s       | 3,657.7              | **5,350.0**                 |
| generation (tg) t/s   | 89.1                 | **126.5**                   |

**D-B が pp で約1.46倍、tg で約1.42倍速い。** section 6 の所見(「CPU オフロードはプレフィルを直撃する」)と整合する結果で、ncmoe=6 の D-A は重みの一部を CPU に逃がしている分だけ確実に遅い。D-B は速度面では明確に有利だが、**KV を q4_0 に落としているため section 10 の落とし穴表にある「tool calling 品質を有意に落とす」という公式の指摘のリスクをそのまま抱える**。今回の計測では tool_use を伴う実タスクでは検証していない(素のテキスト応答のみ)。

### tool_use 実タスクによる比較

section 8 の M1(`/healthz` 追加)・M2(タイムアウト付与)の2課題を、対象 `github.com/mktkhr/rag` @ `c2181d0` に対して D-A/D-B それぞれで実行(`--dangerously-skip-permissions` で無人実行、15分打ち切り)。M0/M3 は今回の目的(tool_use の構造的な壊れ方の検出)には効果が薄い・時間がかかりすぎるため対象外にした。

### 所見・結論

- VRAM: D-A/D-B とも既存 A/B/C 構成と同等の余裕で 256k を収められる
- 速度: D-B(q4_0)が pp/tg・実タスク所要時間のいずれでも明確に有利
- tool calling 品質: 今回の2課題・n=1 の範囲では、q4_0 化による構造的破損(JSON破損・生トークン露出)は確認されなかった。ただし手数(ターン数)がやや増える可能性がある点は継続観察が必要
- **推奨: `ccd` は D-B(q4_0・オフロードなしフル GPU)を採用する。** 既存方針(「q4_0 は tool calling 品質を有意に落とす」)は公式ドキュメントの一般論であり、今回の実測ではこのモデル・このタスク範囲で有意な破損は再現しなかった。ただし n=1・2課題のみの検証であるため、本採用後も M0/M3 や更に長時間のセッションで異常が出ないか継続的に注意すること
- 今回の速度比較は深さ 18k までの計測。256k 域全体での挙動(特に D-A のオフロードがどこまで効くか)は未計測
